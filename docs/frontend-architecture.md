# Frontend Architecture — OdontoFlow Frontend

How the real frontend works: the contract pipeline, the adapter seam, the page patterns, and the testing
strategy. Read this after the README; read [`AGENTS.md`](../AGENTS.md) before changing code.

## 1. The contract pipeline (never hand-written types)

```
backend docs/api/openapi.yaml  (generated by FastAPI at backend HEAD)
   → openapi-typescript
   → src/contracts/api.ts      (components: schemas, paths — GENERATED, do not edit)
   → src/contracts/client.ts   (typed functions + ApiError envelope — written by hand, thin)
   → src/api.ts                (toUi* view models + useMocks dispatch)
   → src/pages/*               (React components bind view models only)
```

Rules that keep this honest:

- Regenerate `api.ts` whenever the backend OpenAPI changes; verify the diff before writing adapters.
- `client.ts` functions are thin HTTP wrappers with generated types; the `Idempotency-Key` header is
  attached on every mutation.
- Errors: axios failures are mapped through `toApiError` into `ApiError {httpStatus, code, message,
  details}` from the backend envelope `{"error": {code, message, details}}`.
- Decimals: backend sends monetary/stock quantities as decimal strings — `toMoneyNumber` converts to
  `number` at the adapter boundary; the backend remains the authority for all math.

## 2. The adapter seam (`src/api.ts`)

Every data function is dual-mode, gated by `useMocks = VITE_USE_MOCKS !== "false"`:

| Function family | Real mode | Mock mode |
|---|---|---|
| `loadCharges`, `registerPayment`, `sumOutstanding` | `GET /charges` + per-charge payments · `POST /charges/{id}/payments` | typed mock store mirroring the real rules |
| `loadInventoryData`, `loadProductBalance`, `loadMovements`, `createProduct`, `registerEntry`, `registerAdjustment`, `registerTransfer` | `/products*` with `location_id` (query for reads, body for mutations) | same rules enforced locally |
| `loadAgenda`, `bookReal`, `rescheduleReal`, `cancelReal` | `/appointments*`, `/slots/query` | typed mocks |
| `loadPatients`, `createPatient` | `/patients` | typed mocks |

View models (`src/types.ts`) are the UI language; `toUi*` functions map the generated types onto them.
Status values (Paid/Pending/Partial, Active/Inactive) are **derived** from real fields — never stored or
mocked as business facts in real mode.

## 3. Page patterns

- **CashPage**: charges table (amount, paid, outstanding, status badge), KPIs derived from real values
  (`Cobrado` = Σ paid, `Por cobrar` = Σ outstanding, `Cargos` = count), payment modal with history +
  register-payment form, loading state, error banner with retry, refresh-after-payment. Overpayment
  surfaces the backend envelope as-is. Columns the backend doesn't project (branch/party/concept/owner)
  render only in mock mode.
- **InventoryPage**: location selector, products table with balance **at the selected location**,
  actions: create product (`{name, unit, kind}`), stock entry at a location (with optional unit price),
  signed adjustment with required reason, transfer origin→destination, kardex modal per Product ×
  Location. KPIs derived from real data (product count, location count, Σ available, zero-stock count).
- **Agenda/Patients**: real adapters over `/appointments`, `/slots/query`, `/patients` (week window in
  the location timezone, UI status vocabulary mapped from backend state).

## 4. Testing strategy

| Layer | Where | What it proves |
|---|---|---|
| Unit/adapter | `test/*-adapter.test.ts` (`npm test`) | Mapping, derivation, mock-mode rules, error envelope; no network |
| Transport | `test/*-transport.test.ts` (`npm test`) | Real-mode paths against mocked axios: URLs, headers (`Idempotency-Key`), envelope mapping, loading/error states |
| Real-backend integration | `vitest.e2e.config.ts` (excluded from `npm test`) | Agenda + Patients adapters against live FastAPI + PostgreSQL with `VITE_USE_MOCKS=false` |
| Pilot E2E | `test/pilot-e2e.test.ts` via `scripts/pilot-e2e.sh` | The full deterministic journey — Patient → Appointment → Visit → Execution → Consumption → Charge → Payment → Cash UI state → Inventory UI state → Transfer — real HTTP, real DB, zero mocks |

Wiring rule: integration specs are excluded from `npm test` in `vite.config.ts`, included in
`vitest.e2e.config.ts`, and excluded from the NodeNext compile in `tsconfig.backend.json`. Register any
new integration spec in all three places.

## 5. Legacy simulator (reference only)

`src/domain/`, `src/simulation/`, `src/server.ts`, `db/` and `docs/architecture.md` describe the old
follow-up harness (virtual clock, FollowupEngine, reminder scheduler) with its own PostgreSQL. It is a
behavioral reference for a future backend module and is **not** connected to the real SPA. Do not build
new features on it.
