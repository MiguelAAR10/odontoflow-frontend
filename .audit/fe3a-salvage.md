## Backend capability canonical at e6d9bf2

The commit is the published FE3A backend (`feat: implement FE3A
service-to-cash backend`) and is already `origin/main`. Its OpenAPI JSON/YAML
and migrations are part of that commit.

Canonical additions:

- Migrations `0016_visit_appointment_uniqueness`,
  `0017_payment_reconciliation`, and `0018_charge_follow_up`.
- Clinical chain: patient create/list/search/read; visit create/list/read;
  visit execution list/create; organization-scoped execution listing with
  `charged`, patient, visit, and execution-date filters.
- Attendance invariant: `POST /visits` accepts either
  `{patient_id, appointment_id}` or `{patient_id, practitioner_id, location_id}`;
  the two origins are mutually exclusive. Appointment-origin visits require a
  confirmed appointment and derive practitioner/location from it. Creates are
  idempotent.
- Checkout primitives: `POST /visits/{visit_id}/executions` and
  `POST /executions/{execution_id}/charges`. Executed price is operator-owned;
  charge amount defaults to that snapshot; one charge per execution; amounts
  must be positive.
- Charge projection/listing: context fields for patient, service, visit,
  location, practitioner, execution time; derived `paid`/`outstanding`; filters
  by execution, patient, location, visit, status, and creation dates.
- Payment/reconciliation: typed methods `efectivo`, `tarjeta`, `yape`, `plin`,
  `transferencia`, `link_pago`; digital methods require a reference; optional
  receiver and reconciliation note; all-payments worklist; one-way
  `POST /payments/{payment_id}/verify`; historical null references remain
  non-verifiable in the frontend policy. Payment creation is idempotent,
  locks the charge, and rejects overpayment.
- Collection follow-up: open/list per charge, worklist list, reschedule, close;
  `state`, `active`, `due_on_or_before`, patient, and location filters;
  clinic-local promised dates; active debt requires open state plus positive
  outstanding; final payment closes an open follow-up atomically.
- Existing canonical scheduling paths remain available for agenda reads,
  slots, reschedule, and appointment-only cancellation.

## Incomplete or unsafe surfaces

1. **S1 blocker — invalid appointment-origin visit payload.**
   `src/components/AttendancePanel.tsx:163-168` sends `appointment_id` together
   with `practitioner_id` and `location_id`. The canonical backend
   `VisitCreate` validator explicitly rejects that combination; appointment
   origin must send only `patient_id` and `appointment_id`. The adapter tests
   call the adapter with the exclusive shape and therefore do not catch the UI
   defect.
2. **Mock patient creation does not honor its idempotency key.**
   `src/api.ts:createPatientRecord` creates a new `Date.now()` row in mock mode
   without reading/saving a receipt, while real `POST /patients` is
   idempotent. This is adapter-parity debt in the S1 flow.
3. **Mock patient history can attach the wrong charge.**
   `loadCharges(params)` returns all `mockCharges` in mock mode and ignores
   `execution_id`. `loadPatientHistory` then takes the first row for each
   execution, so a non-first mock execution can display another patient's
   charge/follow-up.
4. **S2 missing promised-date quick filter.**
   `CashPage` only loads `active: true`; it does not expose the planned
   “vence hoy o antes” control even though `GET /follow-ups` supports
   `due_on_or_before`.
5. **S2 modal state leak.**
   After a successful follow-up mutation, `selected` remains populated while
   `followUpAction` is cleared. The payment modal condition can therefore reopen
   immediately. The selected charge must be cleared as part of that flow.
6. **Patient surface still contains noncanonical display scaffolding.**
   Real-mode `toUiPatient`/`PatientsPage` supplies fixed status/treatment/origin/
   interest and fixed KPI/pagination values even though `PatientRead` projects
   none of those fields. This predates part of the FE3A history addition but is
   unsafe to claim as a complete canonical patient surface.
7. **Verification gate is open.**
   No accepted manual-browser FE3A evidence or zero-error real UI run exists;
   the checkpoint explicitly says prior Playwright/Chromium artifacts are not
   acceptable under the current owner rule.
